# StreakPact 产品重设计:Period 挑战制 + 游戏化(定版 spec)

> **状态:定版(FINAL)—— JX 反馈已并入,2026-07-28。**
> 本文是**已定型的设计规范**,不再是讨论稿。**以文末《决策记录 D1–D8》为准**;上方各节是
> 背景与设计说明,已按决策更新,被否决的方案保留作为理由记录。
> 实现分期见 `docs/ROADMAP.md` 的 "Product redesign: Periods & Gamify" 段(P1 → P2 → P3)。

## 背景与痛点

- 2026-07 月两人几乎停用。根因:当前模型里"每月打卡"是隐式默认,产生了 Google Sheet
  时代没有的持续压力(sheet 留空即可,app 永远在"等你打卡")。
- 结论:打卡从"默认存在"改为"主动发起"。

## 设计一:Period 挑战发起制(定版)

- **默认状态 = 休眠**:无进行中挑战,首页显示空状态,零打卡义务。
- **发起**:任一方可发起,直接生效(两人信任基础,无需对方确认;对方未响应前自己先打卡,
  被取消是发起方自担 —— 多用户化后需加确认流程)。
- **时长(D1)**:第一版**固定 4 周**,周一对齐;发起后从**下一个周一**开始(发起当天恰为
  周一则当天开始)。**自定义时长第一版不做**,想法保留(未来可放开任意 N 周)。
- **中途修改(D7)**:每期**一次**、仅限**前半期**(4 周制 = 前 2 周);一次过修改全部任务
  —— 可删任务(需 confirm)、可调低或调高目标,修改后**至少保留 1 个任务**;使用时弹"唯一
  机会"确认。**替代**现有"每任务每月一次编辑(`edit_count`)"规则。
- **数据结构预留**:`mode` 字段(solo / duo,现只用 duo)、发起人字段。
- **单人打卡**:不做,仅记录想法。

### 结算:单层挑战制(定版,D2)

- **定版:单层(原选项 Y)。** period = 一个不可分割的挑战,只看**总量目标**(如 4 周内早起
  ≥22 天、编程累计 ≥440 分钟)。**删除**周结算、周奖惩、双方周 gate;**期末一次结算**,只有整
  期奖惩(团队)。
- **容错**折算进总量目标数字,由用户**发起时自定**(如 4 周 28 天里定 22 天达标 = 允许 6 天
  没做到)。
- **UI 保留每周进度参考线**:纯展示 pace 提示(当前累计 vs 匀速应达到的量),**不结算**。
- **被否决:双层(原选项 X)** —— 保留周 / 月两套结算与周奖惩。否决理由:每期要写 4–5 份周
  奖惩负担重,且结算状态机复杂(周 lock、双方周 gate 全套)。单层让"每周写奖惩"的负担直接消失。
- **连带简化**:时长规则随单层简化 —— period = 从某周一开始的 N 周(第一版固定 4),不对齐自
  然月,月中发起即从下周一开始,**无"残月按比例"规则**(该规则随双层一并废弃)。

## 设计二:金币经济 + 商城(定版,D3 / D5 / D6)

- **动机**:每周手写奖惩麻烦;现有"券文化"(补签券 / 奶茶券 / 外卖券)已是半道具系统,商城
  是其正规化。注:单层结算下已无周奖惩,商城因此是**可选趣味 + 记录激励层**,非核心闭环,
  优先级排在结算闭环之后(见 ROADMAP P3)。
- **金币获取(D5,起步数值,用一期后可调,两人统一)**:
  - 签到:**5 / 天**
  - 次数型打卡:**10 / 次**
  - 时长型打卡:每 **10 分钟 = 2 金币**,**单任务单日封顶 60 分钟**(即单任务单日上限 12 金币)
  - 挑战成功:**500**
  - 挑战失败:**不扣金币**
- **商城(D3):统一商城、统一定价、商品混放**(通用商品 + 个人化商品共存,不再各自独立定价)。
  锚定价:
  - 补签(签到):**直接扣 20 金币 / 次**(见 D6)
  - 奶茶券:**300** · 外卖券:**400** · 大额奖励:**~1200**
  - 现实券:手动兑换、可设有效期;虚拟物(称号 / 头像框等)优先级低,portfolio 展示价值。
- **补签(D6)**:打卡补签**免费**(现状不变);签到补签**扣 20 金币 / 次**(参照不背单词:金币
  直扣,**不引入补签卡道具**)。
- **防作弊**:金币奖励的是**记录行为**;两人**互见 + 信任约束**防假填,**不做技术防刷**。

## 设计三:Deposit 押注制(定版 —— 记账版,D4)

- **第一版直接采用"记账版"**:发起时双方各自填**押注声明**(押什么 + 失败如何执行),**app 只
  记录、不碰钱**。
  - **成功** = 押注解除 + 发放金币(挑战成功 500)。
  - **失败** = 生成"待执行"账本条目(`reward_ledger` 的 penalty),沿用现有惩罚执行流程(手动执行)。
- **参考 StickK**(耶鲁行为经济学):押金 + 失败捐给 anti-charity,达成率翻倍;我们现有的"打赏反
  女权主播"惩罚就是自发 anti-charity,已验证有效。
- **真钱托管版:明确永不做。** 理由:双货币 / 合规复杂度高;而"真实感"完全可由**手动执行**复刻
  —— 记账 + 信任执行已达到行为经济学要的效果,托管真钱是纯负担。

## 设计四:签到(定版,独立小功能,D8)

- **独立于打卡**:签到 = 每日一次、鼓励每天打开记录,**不绑定任务达标**。
- **断签无惩罚**(与"去压力化"初衷一致);**可补签**,签到补签**扣 20 金币**(见 D6)。
- 金币:签到 **5 / 天**(见 D5)。

## 决策记录(FINAL,2026-07-28 JX 反馈已并入)

> 以下为最终决策,本文其余部分据此更新。

**D1 · 发起制**:确认采用。时长第一版固定为 4 周(周一对齐),发起后从下一个周一开始(或发起当
天若恰为周一)。自定义时长:不做(设计文档保留想法)。

**D2 · 结算**:单层挑战制(选项 Y 定版)。删除周结算 / 周奖惩 / 双方周 gate。整期只看总量目标
(如 4 周早起 ≥22 天、编程累计 ≥440 分钟),期末一次结算。UI 保留每周进度参考线(纯展示 pace,
不结算)。容错折算进总量目标数字,由用户发起时自定。
**撤销结算无时间限制** —— 信任制、双人,**已定,勿再纠结**:任何时候都可「撤销结算」回到待结算并
重新结算,不设时限(与旧模型的 un-settle 一致)。

**D3 · 商城**:统一商城、统一定价、商品混放(通用 + 个人化共存)。

**D4 · 押注制**:第一版直接采用"记账版"—— 发起时各自填押注声明(押什么 + 失败如何执行),app 只
记录;成功 = 押注解除 + 金币,失败 = 生成"待执行"账本条目(沿用现有惩罚执行流程)。真钱托管版:
明确永不做,理由记入文档(双货币 / 合规复杂度 / 真实感可由手动执行复刻)。

**D5 · 金币经济(起步数值,用一期后可调)**:签到 5/天;次数型打卡 10/次;时长型打卡每 10 分钟 =
2、单任务单日封顶 60 分钟;挑战成功 500;失败不扣金币。商城锚定价:补签(签到)直接扣 20 金币/次、
奶茶券 300、外卖券 400、大额奖励 ~1200。设计说明:金币奖励的是记录行为,两人互见 + 信任约束防假填,
不做技术防刷。

**D6 · 补签**:打卡补签免费(现状不变);签到补签扣 20 金币(参照不背单词,金币直扣,不引入补签卡
道具)。

**D7 · 挑战中途修改**:每期一次、仅限前半期(4 周制 = 前 2 周)、一次过修改全部任务(可删任务需
confirm、可调低或调高目标、修改后至少保留 1 个任务)、使用时弹唯一机会确认。替代现有"每任务每月一
次"规则。

**D8 · 签到**:独立于打卡,每日一次,断签无惩罚,可补签(见 D6)。

**D9 · 开赛日自动作废**:挑战到 `start_date`(周一)仍无对方加入(只有发起人一个 member)→
自动作废,回到休眠并简短提示。检测在 load 时;因 RLS 仅发起人可改挑战,发起人的客户端惰性写入
`cancelled`,双方 UI 立即按"作废"渲染为休眠(与结算 reconcile 同一模式)。发起人开赛前手动取消
仍保留。

**D10 · 编辑机会自开赛起算**:`start_date` 之前双方可自由修改任务 —— 不消耗机会、无"唯一机会"
弹窗。"一次 · 仅前半期"的唯一修改机会(D7)自 `start_date` 起才开始计。

**团队奖励字段(team_reward)**:落实 D2 的"整期奖惩(团队)"—— `challenges` 增加可选
`team_reward` 文本字段(发起时设),双方通关时作为共享奖励写入各自 `reward_ledger`(沿用旧月度
共享奖励的位置)。个人奖励是金币(D5),失败侧由各自押注声明(D4)覆盖,故不设 `team_penalty`。

**D11 · 取消 / 中止**:**开赛前**发起人可单方取消(回到休眠,保持现状)。**开赛后不再有单方
取消** —— 单方取消是即将失败一方的逃生舱,一键让押注蒸发,掏空押注机制。改为「**中止**」,需
**双方同意**:任一方发起中止请求,对方看到 banner 后确认,即协商中止 ——**void、不结算、不执行
押注**(是协商解散,不是失败)。对方确认前发起方可撤回。
- **落地(schema 选择)**:每个 `challenge_members` 增加可空列 `abort_requested_at`;发起 = 置自己
  的时间,确认 = 对方也置自己的,**两边都置 = 中止**。各自只改**自己的** member 行(沿用 own-row
  RLS,无需放宽 challenges 的写权限)。两边都置后由**发起人客户端惰性写** `challenges.status =
  'aborted'`(与 D9 自动作废同一模式);`status` 增加 `'aborted'`,与开赛前单方取消的 `'cancelled'`
  区分。
